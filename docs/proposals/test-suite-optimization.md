# Test suite optimization proposal

## Decision

Give feature work a fast verification command and keep the complete acceptance suite in the release gate. Start browser tests from validated saves when their assertions begin after travel, combat, or a purchase. Keep full player journeys for the requirements that depend on the whole journey. Consolidate checks that observe the same behavior at the same layer, and use failures caused by deliberate regressions to verify the remaining coverage.

## Baseline

The 17 November 2026 release evidence for `0.2.0-rc.1` records **54m 41s** across sequential gate steps on one machine. Playwright took **37m 45s**, and Vitest integration took **14m 22s**. Together they accounted for about **95%** of gate time. These are recorded timings, rounded to seconds. The current Playwright listing still discovers **78 distinct scenarios in 22 files** across the main Chromium projects. This review used existing reports for timing and did not rerun the full gate. The local timing evidence is in `reports/release-gate.md` and `reports/release/results/`, and the checked-in candidate records the pass counts. The critical path is concentrated. Playwright's progression journey took **14m 04s in Chromium** and **14m 18s in Firefox**, close to the total wall time of each browser project with parallelism already enabled. It plays two sorties at 1× and uses one-second polling in its fight loop. In Chromium, starter combat and refit took **4m 07s**, loss and recovery **3m 28s**, the guided first loop **2m 30s**, and the offline loop **2m 25s**. Those scenario durations overlap. The offline loop also dominates both branded smoke projects, at about **2m 19s each**. Accessibility is a better target for removing repeated setup and audits than for the largest wall-time savings. The working tree contains **167 test and spec files**, about **36,600 nonblank lines** of test and support code, and about **25,700 nonblank lines** of fixtures. The counts describe different costs. For example, `messageCatalog.test.ts` accounted for 243 recorded cases, largely through key-by-key registration, while four large golden saves account for about 420 KB of fixture data. The latter preserve valuable state and compatibility evidence. Prioritize repeated behavior and setup before reducing case counts or fixture bytes. ## Run after a feature or a release

| When | Run | What it should prove |
|---|---|---|
| After a feature, also suitable for pull requests | A proposed `npm run verify:feature` with typecheck, architecture and content validation, unit and component suites, fast integration, traceability, and a small Chromium Playwright smoke project served from one fresh production build. | The game boots through the real worker, creates and reopens a campaign through IndexedDB, completes a station transaction, accepts a navigation or combat command from a prepared save, and passes a representative keyboard and axe check. Keep subsystem-specific Vitest and Playwright filters available for iteration. |
| After changes to combat, navigation, economy, or authored balance | The subsystems above plus the affected fixture-based browser tests and relevant headless scenarios. Run the full balance suite when shared combat, economy, pilot policy, or tuning semantics change. | Fast feedback on the affected rules and a full comparison when a change can alter results across fits, sites, or careers. |
| Before a major release or when recording a candidate | `npm run release:gate` with full headless balance, ladder, replay, persistence and properties, isolated performance tests, the production build audit, and the retained Chromium and Firefox browser and accessibility suites. Keep the optional branded smoke and the separate human playtest. | Complete release evidence for a single source digest and build fingerprint. Preserve the guided and destroyer journeys, the required browser and accessibility surfaces, and one complete offline sortie. |

Use explicit Playwright tags or project filters for feature smoke and long journeys, with the full release projects including both. Keep `verify` and the release gate semantics during rollout. Split deterministic fast integration into a named selection and put `balance/**`, the long progression suites and the full site ladder in the release selection. A single headless Scout scenario with fixed seed, expected bounty, and conserved cargo/credits is a candidate for feature smoke once its runtime is measured. Include both selections in the release gate and retain its report inputs. Verify that release discovery covers feature smoke and the long suites without running the same case twice in the same browser. The current `V02-AC-14` extent explicitly calls for the whole browser suite in Firefox, so further Firefox sampling requires a change to that scope. ## Reach browser test states faster

**Start with saved checkpoints outside the shipped app.** Add one Playwright fixture helper that prepares a named save in an isolated context and resumes it through the real UI. Generate the checkpoint from the same compiled content as the served build, using the existing headless scenario driver and save service. Use the current persistence adapter on an inert same-origin setup page before the app or its worker opens the database, or capture Playwright storage state including IndexedDB once per checkpoint for that run. Match the worker's database and origin, including the slot manifest and snapshot. Validate save format, content identity, checksum and the expected initial UI state, and fail setup clearly when they diverge. Pause the checkpoint at a reproducible boundary. Continue through the actual UI, gateway, worker and persistence for the behavior under test. Existing headless builders and golden states are starting points. The current `fund()` helper shows that a production build already resumes prepared state, but it mutates and reseals an existing save. Replace that setup with a funded checkpoint where the market or ship-switch action is still performed by the test. [Scenario session](../../tests/support/progression/session.ts) · [Golden checkpoint definitions](../../tests/support/golden/campaign.ts) · [Browser funding setup](../../tests/support/funding.ts) · [IndexedDB adapter](../../src/adapters/persistence/indexedDbSaveStore.ts)

| Checkpoint | Keep exercising in the browser |
|---|---|
| Paused Scout, target in range and initially unlocked | Select, lock, fire and stop using the mouse or keyboard. Use a separate active-fight state for expanded explanations, focus and axe scans. Keep real undock, warp and dock in the navigation acceptance test. |
| Guided projectile in flight or an active web | The visual marker, equivalent text, reduced-motion behavior and effect attribution. Keep launch and reload behavior in the dedicated guided journey and exact timing/expiry in headless tests. |
| Scout wreck in range or freshly destroyed and shipless | Looting or recovery via the real controls, including the loss report, refusal text, recovery purchase, or save and reopen as appropriate. Keep one browser transition through destruction in the release lane. |
| Returned from Patrol with salvage, or prepared for the advanced site | Sell or fit the earned item, repair/recharge, and verify reopened wallet, fit, completion, or destination state in separate tests. Keep a full release journey where earning and spending the same value is the assertion. |

**Add manual time stepping only where a checkpoint leaves an important transition too slow.** `createFrameDriver` already accepts a clock and scheduler. Pilot a separate Playwright or compile-time test entry that uses those seams and sends normal `time.advance` commands sequentially. Wait for command acknowledgement and the relevant projection before making the next UI assertion. Authored time rules support 1×, 50 ms simulation quanta, and a 250 ms frame cap, so sending one huge elapsed delta discards time. Use capped steps and pause or stop at observable boundaries so a projectile or lock state remains visible. The campaign suspension test already uses `page.clock.fastForward()` to prove the clamp, and is a good example of why clock fast-forwarding alone does not speed up a sortie. Preserve real-clock coverage for pause, suspension, and the representative full journey. Keep any step control or fixture bridge out of production entries, worker bundles and the public protocol, and check this in the production build. [Frame driver](../../src/gateway/frameDriver.ts) · [Time rules](../../content/rules/time.json) · [Suspension test](../../tests/browser/campaign.spec.ts#L98) · [Development tools policy](../02_TechnicalSpecification.md#16-diagnostics-and-development-support)

After the fixed-state pilot, remove repeated bootstrap code. Standard Playwright tests already have isolated contexts, so ordinary fresh-campaign setup can navigate once and start the campaign. Keep explicit IndexedDB manipulation in tests that exercise existing, corrupted, or incompatible storage. Consolidate the repeated RNG seed shim, transaction confirmation, and axe setup. Wait for a visible expected outcome or an enabled confirmation. The disappearance of `Calculating…` can pass before a preview ever arrives. Keep pointer and keyboard actions explicit in input tests. Where the release progression pilot still polls, replace broad catch-and-retry with explicit reasons for transient unavailability and report the current target, weapon state and last observed projection on failure. ## Reduce headless release time separately

The matrix runs **12 sites × 6 fits × 10 seeds**, with 13 declared comparison cases. The matrix, other balance cases, site ladder and progression files total about **97% of summed integration case time** in the recorded run. Individual careers took **12m 04s** for no module drops, **10m 34s** for cruiser-loss recovery and **9m 59s** for the full hull ladder. They already run headlessly. Their distinct assertions cover ordinary economic progression, a no-drop route, and a viable recovery after losing an upgraded hull. These are good release checks and poor feature defaults. [Matrix fixture](../../tests/fixtures/balance/matrix.json) · [Ladder tests](../../tests/integration/siteLadder.test.ts) · [Career fixtures](../../tests/fixtures/balance/careers.json)

1. Profile a slow matrix cell and a slow career. The scenario driver sends one protocol advance per 250 ms of requested real time, and the host creates transaction drafts and checks invariants. Measure engine advancement, state copying and validation, pilot queries, and report serialization before deciding which cost to reduce. Preserve ordinary protocol execution for replay and at least one complete career. Consider a faster headless balance path only if it matches checkpoints, event order, resource totals and report figures for the same seed and policy. Keep the timed performance suite isolated. [Advance loop](../../tests/support/progression/session.ts#L81) · [Transactions](../../src/engine/application/transaction.ts) · [Pilot](../../tests/support/progression/pilot.ts)
2. Reuse identical measured sorties only when starting state, fit, site, seed, command policy and measured outputs match. `base.lancer` in the prepared mastery suite and the long-range career are candidates for comparison. The former isolates fit viability and writes scenario figures, while the latter proves that ordinary earnings buy the fit. Likewise the site ladder proves consecutive clears and full bounty, while the fit matrix compares competing fits. Keep these distinct assertions. Reduce the breadth of any overlapping run only after confirming the retained evidence satisfies its original requirement. [Mastery tests](../../tests/integration/progressionMastery.test.ts) · [Long-range career](../../tests/integration/balance/careerLongRange.test.ts) · [Balance report inputs](../../scripts/balance-report.mjs)
3. Once the longest case is measured after refactoring, consider splitting matrix work by independent site or seed batches and merging results deterministically. Tune worker count with the same workload before adding workers. The current balance reporter reads sections from a shared directory and checks that expected section IDs are present. Have the release runner assemble sections from a fresh run directory and verify run identity, content/source identity, and all expected seeds, cells and careers. This prevents a fast or exploratory run from reusing earlier balance evidence. ## Rollout and acceptance

1. **Split and measure.** Add the feature command and explicit selectors first. Record total wall time, build/setup time, slowest individual case, browser and worker count, and retries on the same machine. Capture at least three comparable runs and use the median. The first target is **under two minutes** for feature verification, including **under one minute** for its Chromium smoke. These are targets to validate against the baseline.
2. **Pilot checkpoints.** Convert the combat accessibility setup and one progression UI slice first. Confirm the checkpoint-backed cases fail with a broken lock command, missing accessible combat status, or incorrect restored fit. Compare runtime and retained behavior before replacing the long setup elsewhere. Decide whether to keep the old 14-minute progression script intact by checking which reward-funded, repeatability and reopen assertions are already demonstrated in the retained release journeys and headless runs. With that evidence in place, retire the duplicated route or keep its unique portion as a focused release scenario. Target comparable full-gate wall time **below 35 minutes** after the critical-path changes.
3. **Prune with evidence.** For each deletion, name the retained assertion and the regression it catches. Verify representative failures by temporarily breaking a transaction, a focus return, and a preview or schema guard in an isolated checkout. Update requirement IDs only on cases that exercise them and rerun `npm run traceability`. Check that no included requirement loses played-loop evidence and that `V02-AC-14` still has its required browser coverage. Have the gate verify that required long journeys and accessibility variants ran. Currently a Playwright step can report success with some passing cases even when its selection is narrower than intended. Finish with a full gate run that generates the expected balance and release reports against the fingerprinted production bundle.
